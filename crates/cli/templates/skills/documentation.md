# Documentation

Write documentation a reader can act on. Start from the question the reader
arrives with, not from the structure of the code.

## Steps

1. Identify the reader and what they want to do after reading.
2. Put the answer first: what it is, when to use it, one working example.
3. Verify every command and snippet by running it.
4. Document the reasons behind non-obvious choices, not what the code says.
5. Link to details instead of copying them, so there is one source of truth.
6. Update the docs in the same change as the code.

## Style

- Short sentences and concrete nouns.
- Use the same term for the same thing throughout.
- Show inputs and expected output for examples.
- State limits, defaults and error cases.

## Avoid

- Marketing adjectives with no evidence behind them.
- Restating a function name as its description.
- Instructions that were never run.
